# 通信・安定性の改善 — 160.4

## 3方式の確認

|方式|処理|今回の改善|
|---|---|---|
|従来方式|検索ページHTMLから候補取得、詳細でNG判定|応答本文の取得まで15秒のタイムアウト。先読みループ内で上限と有効設定を確認。検索URLを固定し、ZenzaWatch中の動画URLへ通信しない。|
|API併用|Snapshot検索後に詳細でNG判定|途中ページで検証後の取得位置が100へ戻る不具合を修正。取得済みの窓の末尾から続行。少数件でも照合不足なら従来方式へ戻る。|
|API高速|APIで明確なNGを除外してから必要な詳細判定|併用方式と同じ位置・上限修正を適用。空応答は終端、不正JSON構造はエラーとして従来方式へ切替。タグロック・複合NGの詳細判定は維持。|

設定の追加取得上限はHTMLページ数またはAPI取得回数です。APIは1回最大100件で、検証に使った取得分も候補へ再利用されます。設定説明にも明記しました。取得方式変更の反映には再読み込みが必要です。

## 詳細取得

同時数を下げた後に新しい通信を入れてしまう不具合を修正しました。既に通信中の要求は中断せず、空き枠ができるまで次を待ちます。初期値も1〜20へ制限します。

同じ要求に複数の終了通知が来ても1回だけ処理します。古いタイムアウト要求の遅延通知、通信APIの同期例外、Promiseの拒否、中断も待ち行列を解放します。同期失敗が連続しても再帰でスタックを使い果たさないようにしました。既存の「タイムアウト時のみ1回再試行」は維持し、無制限な再送は追加していません。

## 広告通信

広告の装飾と広告者照合は異なるAPIです。装飾OFFでも警告・広告関連の複合NGがONなら照合通信は必要であり、説明を追加しました。

- 両用途合計で最大4件同時。同一動画・同一用途の実行中要求は共有。
- 装飾取得も本文まで10秒でタイムアウト。装飾済みカードの二重装飾を防止。
- 広告者照合の失敗は30秒間再利用して連打を防ぎ、その後の照合要求では再試行可能。自動的な無限再試行はしません。
- 応答構造が不正な場合や、広告者一覧が上限100件に達した場合は、全件確認できたと扱わず判定保留。100件以上の一覧を完全照合する拡張は行っていません。

## 保存とUI

詳細キャッシュは1件ごとの全体保存から200ms単位のまとめ保存に変更しました。メモリー内の反映は即時で、pagehideで未保存分を保存します。テストでは50件の連続追加を1回の保存にまとめられました。ブラウザー強制終了などpagehideが発火しない終了では、直近の最大200ms程度のキャッシュが保存されない可能性があります。NG設定の保存方式には変更ありません。

不正な保存時刻のキャッシュは無効化。開発者モードOFFでは候補一覧の大きな表を生成しません。方式変更の反映時期、取得上限の単位、広告用途の違い、保留条件を設定画面へ追記しました。

## 検証

自動テスト95件、構文チェック、Braveの独立したヘッドレスプロファイルでのリスト／タイル試験が成功しました。主な追加試験は以下です。

- 3方式の上限・検証後の取得位置・少数件不一致・空／不正応答。
- 同時数変更、二重通知、タイムアウト後の遅延通知、中断、同期例外10,000件、Promise拒否。
- 広告の共有・同時数上限・エラー後の枠解放・失敗キャッシュの期限。
- 本文受信中のタイムアウト、キャッシュのまとめ保存とpagehide保存。
- 再生中も検索条件とページ番号を保持。

通信先の実APIへの負荷試験や、ログイン中のBrave＋Tampermonkey＋ZenzaWatchを通した実地試験はしていません。速度の実測比較も未実施です。添付ログの全ての外部スクリプトの警告を本スクリプトの不具合とみなしてはいません。

## 今後の確認対象

Snapshotはサイト検索との更新時差や並び順差を完全には解消できません。現在の照合・従来方式への切替を維持しています。広告者100件以上の全件照合、実APIでの速度比較、初期表示時の詳細キャッシュ復元と通信開始順の最適化は、追加の実地確認とテストを伴う別の改善候補です。
