# 160.12 項目別取得状態と詳細通信の省略

## 対象

製品160.11（43bc180）から分岐した `codex/field-readiness-20260920`。研究R25（1799cb7）の引き継ぎを参照し、取得済み投稿者情報の保持と項目別の取得要否だけを実装した。研究リポジトリ・別の開発worktreeは変更していない。snapshot / playlist/requestの一括補完は追加していない。

## 動作

- 投稿者ID・種類・名前・表示状態、タグ・ロックタグ・説明文を `unknown / known / failed` で管理する。空配列・空文字を確認した場合だけ既知の空とする。
- `ownerType:hidden, type:user, id:有効値, name:null` でもIDと種類を保持する。hiddenを退会や削除と扱わない。
- 型不明・型矛盾・無効IDを拒否。user/channelは同じ数値でも別の識別子。ch接頭辞は明示的なchannel型または正規のchannel URLに限る。
- カードの動画ID、登録時の動画ID、取得応答内の動画IDを照合する。検索由来の競合は未確定に戻し、検証済み詳細の優先順位は維持する。
- ownerだけで `thumbInfoDone` を立てない。取得の終了と「今必要な項目がそろった」状態を分け、画面と自動継ぎ足しの待機も後者を認識する。
- AND/OR/NOTやnotExistsは項目が不明なら保留を維持する。投稿者名が不明の自己広告照合も不一致と確定しない。後から名前・IDが判明した場合は保存済み広告者一覧で再計算する。
- 現在の基本NG・複合NG・表示設定から必要項目を求める。同じルールの項目一覧を繰り返し解析しない。設定変更は再評価し、同時の要求をまとめる。
- 閉じた詳細欄は開く操作で取得する。遅れて届いた説明文を再描画し、手動の開閉状態を維持する。
- 直近キャッシュ、要求の重複抑止、同時数・タイムアウト、SPA破棄は維持する。セッションキャッシュは項目状態を保存する形式3へ変更し、状態の判別できない旧形式2は再利用しない。

## 通信省略の根拠

| 条件 | 通信モックでの確認 |
| --- | --- |
| 検証済み投稿者ID・種類があり、投稿者IDのみの条件、詳細を閉じた状態 | 個別詳細要求0件 |
| 上記からタグ条件を追加 | 対象動画へ1件。繰り返し要求しても増えない |
| 既知カードの詳細を開く | そのカードへ1件 |
| タグ・ロックタグ・名前・説明文が必要で未取得 | 個別取得を行う |
| 同一ルールで100回取得要否を計算 | 必要項目のルール解析1回。ルール変更後は再解析 |

これらは通信モック・通信を遮断したブラウザ試験の結果。実サイトの秒数・速度倍率や全検索結果での削減率は測定していない。投稿者を確認できないカードでは個別取得が残る。旧セッションキャッシュの更新直後も再取得が発生する。

## 検証

改修前は107件の既存テストが成功（古い生成物ファイル名を参照していたcore試験を修正後）。今回の回帰試験を含め126件が成功。構文・プライバシー検査と、通信遮断ブラウザの5種類の試験も成功した。

```text
node scripts/test.mjs
node scripts/check.mjs
node scripts/check-privacy.mjs
node scripts/test-metadata-readiness.mjs
node scripts/test-owner-evidence.mjs
node scripts/test-spa.mjs
node scripts/test-result-layout.mjs
node scripts/test-card-enhancements.mjs
```

ブラウザ試験はPlaywrightとブラウザ実行ファイルを `NRN_PLAYWRIGHT` / `NRN_BROWSER` で指定する。個人のプロファイルやログイン情報は使用せず、全通信を架空URLの応答へ置換する。固定された個人環境パスをスクリプトに保存しない。

別担当のレビューで、遅延説明文・旧キャッシュの空値・自己広告照合の不明状態の3点を再現し、回帰テストを追加して修正した。

## 残る条件と次の単位

- 実ニコニコ、利用中のユーザースクリプト管理拡張、実際の検索・ランキングページでは未検証。インストール操作や公開先の変更は行っていない。
- 詳細APIでも取得できない情報は不明のまま保留する。同じSPA世代で失敗した要求を無制限に再試行しない。
- 検索初期データの新規収集や別の投稿者API照会は追加していない。現在のカード・既存取得経路にある、検証できる投稿者情報だけを利用する。
- 次は少数の実ページで適用条件を確認し、その後snapshot補完とplaylist/request補完を別々に評価する。鮮度・欠落・型・順序・ロックタグの有無を区別する。
- 公開前の過去履歴整理は、他タスクの製品進捗と共有履歴を維持して別途統合する。現在ツリーの環境パスと画面資料は匿名化し、認証値・blob URL・実閲覧ログを成果物に加えていない。
