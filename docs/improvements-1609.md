# 160.9 ページ送り・投稿者欄・広告修正

## 変更と使い方

- SPA対応ON・ページャー「範囲圧縮」で、全動画の表示またはNG処理を終えた追加ページを斜線付きの無効な範囲へまとめる。現在ページは枠で表示する。
- 例：3ページで4～8を処理済みなら `← 1 2 [3] 4–8 9 10 … 最終 →`。次は9。9で10～13を処理したら `← … 2 3 4–8 [9] 10–13 14 15 … 最終 →`。前は3、次は14。10～14は5ページ分。
- 先読み済みでも未表示・未判定・取得失敗の動画が残るページは無効化しない。追加候補や予備カードを捨てて先へ飛ばすことはしない。判定済み範囲の記録は同じタブ内のSPA移動で維持し、検索条件とNG設定で分離する。再読み込みでは消える。
- 範囲記録は最大8検索、各256ページ、30分。現在地の履歴は128件、取得ページのID照合表も256ページまで。永続保存や追加通信は行わない。
- サイト側の初期化済みReact Routerが使える場合だけ独自ページャーを表示する。`navigate()`でサイト自身に画面遷移を依頼し、履歴だけを書き換えたり、再読み込みしたりしない。未対応・接続失敗時は元のリンクを残す。API方式にはHTMLページの範囲を適用しない。
- 最初の←と最後の→は灰色で無効。範囲もhrefのない要素なのでキーボードでも誤って移動しない。検索中にNG設定が変わった場合はクリック時にも古い範囲を再検査する。
- 投稿者欄は閉じているときは元の場所、詳細を開くとアイコン・名前・NGボタンを詳細欄に表示する。元の投稿者要素は移動・複製せず、詳細が用意できた時だけCSSで隠す。「投稿者情報」「ユーザー:」の見出しを削除。
- 追加カードの広告装飾で、投稿者名を「提供」と誤表示していた処理を削除。装飾APIのownerNameを広告主だと解釈しない。確認できるポイントとリボンを残す。元サイトの正規の提供表示は変えない。

## 検証と制限

自動テスト101件、構文確認、専用Chromeのページャー・カード・SPA・リスト/タイル・NGエディター試験が通過。専用Chromeは空のプロファイル、架空のURL、全通信をテスト応答に置き換えている。ページャー試験では3→9の同一document遷移、未表示ページを飛ばさないこと、設定変更、終端、サイト機能がない場合とエラー時の復元を確認。

**実ニコニコでの動作、Tampermonkeyへの更新は未実施。** 実サイト操作は以前のサイト安全判定で拒否されている。実サイトのルーター公開状況は未確認であり、範囲圧縮の実サイト動作を保証する段階ではない。サイトルーターを読むためunsafeWindow権限を追加した。基準版のファイルは変更していない。

[React Routerの公開実装](https://github.com/remix-run/react-router/blob/main/packages/react-router/lib/dom-export/hydrated-router.tsx)にあるwindow.__reactRouterDataRouterを機能検出する。非公開のReact内部ツリーの書き換えは行わない。

## 追加資料の解析

### iPhoneの非表示機能

画像では投稿者欄のない動画にも「このユーザーの動画を非表示」があり、操作後に一群の動画だけが非表示になっている。これは投稿者単位の識別手段が残っている手掛かりである。数値IDをアプリが取得するのか、動画IDを送ってサーバーが投稿者を解決するのかはまだ分からない。表示名・アイコンの欠落だけで退会を断定しない。古いアカウントと新しいアカウントの差だという証拠もない。

添付されたWebメニューにもdata-value="owner-mute-user"がある。このメニューHTMLには投稿者IDは含まれない。対象動画の検索応答・非表示操作の通信を照合する必要がある。別アカウントが同一人物か、活動期間・件数といった主張は今回の資料では検証していない。

BlueStacksはAndroidアプリを実行する候補だが、iPhone版と同じ通信方式とは限らない。インストールするだけでAPIの中身が自動で分かるわけでもない。今回は導入・アプリ本体取得・解析は行っていない。先にWeb側にも存在する非表示機能のデータを確認するのが、今回の資料から考えられる短い経路。[BlueStacksの公式アプリ導入手順](https://support.bluestacks.com/hc/en-us/articles/360057712191-How-to-install-an-app-from-the-BlueStacks-Store-Play-Store-or-using-an-APK-on-BlueStacks-5)

### ホバー表示

添付のsm90001004のカードには、video-contentのvideo要素、30秒の進行表示、コメント用canvas、空のstoryboard-content、非表示のsupporter-content、あとで見る・メニュー・ミュートのボタンがある。vsc-controllerは別の拡張機能による要素と考えられ、ニコニコの再現対象から除く。

blob:で始まるURLはそのページが保持する一時的な動画データへの参照。元のAPIアドレスではない。canvas内のコメントもHTMLテキストには入っていない。あとで見るの認証・成功/失敗処理、動画の取得応答、コメント取得・時刻情報は今回のHTMLに含まれない。追加カードの操作ボタンと動画・コメントのホバープレビューは**引き続き未実装**。既存カードの動作を妨げない試験と再実装は別である。

### 消える要素の保存方法（Chrome）

1. F12で開発者ツールを開く。Consoleで `setTimeout(() => { debugger; }, 3000)` を実行する。
2. 3秒以内にページの対象サムネへマウスを移動する。処理が一時停止したらElementsで対象を選ぶ。
3. 対象の右クリック → Copy → Copy outerHTML。見た目はスクリーンショットも保存する。
4. F8で再開する。フォーカスを外すと消えるメニューには、開発者ツールのコマンドメニューから「Emulate a focused page」も使える。

:hoverの固定だけでは、JavaScriptが追加・削除する要素までは保てない場合がある。HTMLにはイベント処理・動画の内容・canvasの描画内容は保存されない。通信調査には対象リクエストのURL・メソッド・応答項目が別途必要。Cookie、Authorization、視聴キーを含むHAR全体は送る必要がない。[Chrome公式：消える要素の調査方法](https://developer.chrome.com/blog/devtools-tips-35)

### 「ここから連続再生」リンク

提供されたsm90001005のplaylistパラメーターはBase64のUTF-8 JSONだった。復号結果：

```json
{
  "type": "search",
  "context": {
    "sortKey": "hot",
    "sortOrder": "none",
    "page": 1,
    "pageSize": 32,
    "tag": "テスト用タグ",
    "channelVideoListingStatus": "included",
    "selectContentType": "long"
  }
}
```

watch/sm90001005が開始する動画、continuous=1が連続再生を指定するパラメーター。playlistには動画ID一覧ではなく「テスト用タグ」の検索条件とページ位置が含まれる。sortKey=hotなどの正確な並び順の意味はサーバー仕様の確認が必要。rf/rp/raは添付リンクではnvpc/tag/mainで、流入元の識別に使われると考えられるが、この値だけでは厳密な仕様は断定しない。

同じ構造の検索プレイリストを作る余地はある。ただし、任意の動画ID配列を入れれば公式プレイヤーが再生するという証拠はない。手元に保存済みのMintWatch公開ソースのPlaylist.tsxではmylistIdやseriesIdを渡す形式も見つかるが、現行公式の対応を実機で検証したものではない。任意のNG通過動画だけのキューには、公式側の対応形式の確認か、独自の再生キュー実装が必要。
